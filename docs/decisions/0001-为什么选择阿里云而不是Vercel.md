# 0001 - 为什么选择阿里云而不是 Vercel

**决策日期**:2026-05-13
**决策人**:Reason
**状态**:已生效
**影响范围**:整个技术栈

---

## TL;DR(一句话总结)

**为了服务好中国用户,我们放弃了 Vercel + Supabase 的"开发体验最佳"组合,改用阿里云 SAE + RDS PostgreSQL 的"国内可用"组合。这个决策让运维复杂度上升,但解决了产品在中国能否被访问的根本问题。**

---

## 背景:我们最初是怎么想的?

在产品规划阶段,我们最初定的技术栈是:

```
Next.js + Vercel + Supabase + Stripe + Resend
```

这套组合在 2024-2026 年的硅谷创业圈是"默认选项",原因是:

1. **开发体验极致**:Vercel 一键部署、Supabase 一键搞定数据库和认证
2. **生态成熟**:Next.js 官方就是 Vercel 公司维护的,两者配合最顺
3. **冷启动快**:从 0 到上线,一个人一周就够
4. **成本前期低**:用户量不大时,Vercel + Supabase 加起来每月可能不到 50 美元

如果我们做的是一个只服务海外用户的 SaaS,这套组合**毫无疑问是最佳选择**。

---

## 为什么必须放弃?

### 核心问题:这套组合在中国不可用

Academia 的用户构成是**一半中国大陆,一半海外**。这意味着:

1. **Vercel 在中国大陆访问极不稳定**
   - Vercel 的 CDN 节点不在中国大陆境内
   - 实测从中国主流城市访问 Vercel 部署的网站,延迟 800ms-3s,部分时段直接超时
   - 这不是"体验差一点"的问题,是"用户根本打不开网站"的问题

2. **Supabase 同样面临访问问题**
   - Supabase 数据库托管在 AWS(主要在美东、新加坡)
   - 从中国访问的延迟通常在 200-400ms
   - 这意味着每次数据库查询都要花掉用户半秒钟,产品体验崩塌

3. **数据合规风险**
   - 中国《数据安全法》《个人信息保护法》要求中国公民的个人数据原则上存储在境内
   - 把中国用户的学习记录、支付信息存在境外服务器,在做大之前是灰色地带,做大之后一定被监管
   - 一旦被要求"数据迁回境内",我们的整个技术栈要重做一遍

### 次要问题:支付通道不匹配

- Stripe 在中国大陆无法直接收款(需要海外公司主体)
- 我们的中国用户主要用微信支付和支付宝,这两家都和阿里云有原生集成
- 用 Vercel 的话,微信支付/支付宝的回调链路要绕一大圈

---

## 我们考虑过的备选方案

### 方案 A:Vercel + Cloudflare 国内加速(否决)

理论上 Cloudflare 在中国通过和京东云的合作提供加速,但:
- 需要 ICP 备案,本质上还是要走国内合规流程
- 加速服务每月起步 200 美元,小厂用不起
- 数据合规问题没有解决,数据库还在境外

### 方案 B:海外 Vercel + 国内独立部署(否决)

两套部署,代码 95% 共用,数据用消息队列同步。
- 优点:海外用户体验最佳,国内用户也能访问
- **致命缺点**:**两倍开发量、两倍运维量、两倍出错可能**
- 对一个一开始只有一个人(你)+ Claude Code 的项目,这个复杂度承受不起
- **决策原则**:MVP 阶段不为还不存在的问题花钱

### 方案 C:腾讯云替代阿里云(否决)

腾讯云在某些方面体验也不错,但:
- 腾讯云主推 MySQL,PostgreSQL 生态弱于阿里云
- 腾讯云的 Serverless 产品(SCF)成熟度不如阿里云 SAE
- 微信支付和腾讯云的"原生集成"实际上没有比阿里云强多少
- 阿里云的开发者文档和工具链整体质量高一档

### 方案 D:完全国内方案(已采纳)

```
阿里云 SAE + RDS PostgreSQL + Tair Redis + OSS + DirectMail + 微信支付/支付宝
```

---

## 这个决策的代价(我们必须接受的)

我们要诚实地承认这个选择带来的成本:

1. **运维复杂度上升**
   - Vercel 是"零运维",阿里云 SAE 是"低运维"
   - 你需要管理一些 Vercel 帮你管的事:环境变量、域名解析、SSL 证书自动续期、日志查看
   - **缓解措施**:选择 SAE 而不是 ECS,把运维负担降到最低

2. **生态工具变少**
   - Vercel 周边的 Preview Deployment、Edge Functions、Analytics 都没了
   - 一些 Next.js 高级特性(如 Edge Runtime)在阿里云 SAE 上不能用
   - **缓解措施**:用 Server Actions + 普通 API Routes 替代 Edge Functions,功能上没有真正损失

3. **海外用户体验暂时变差**
   - 阿里云国际节点(新加坡)虽然有,但延迟和稳定性不如 Vercel 全球网络
   - **缓解措施**:海外用户在 MVP 阶段不是核心目标,等国内验证完商业模型后,海外版用 Vercel 重新部署

4. **必须办 ICP 备案**
   - 这是国内合法运营的硬门槛
   - 时间成本:15-25 天
   - 资金成本:几乎为零(阿里云提供免费备案服务)
   - **关键风险**:这是项目能不能上线的关键路径,必须 Day 1 启动

5. **国际化路径变长**
   - 未来出海时,需要重新部署一套海外版
   - 但这个时候我们已经有现金流和用户验证,可以负担

---

## 这个决策的好处(我们想要的)

1. **中国用户能正常访问**——这是底线
2. **数据合规**——长期可持续
3. **支付通道顺畅**——微信支付/支付宝原生集成
4. **成本可控**——MVP 阶段月成本 200-500 元人民币,比 Vercel 还便宜
5. **未来弹性好**——用户量上来后,阿里云的扩容能力顶级,不会被基础设施卡住

---

## 关联决策(一并锁定的子决策)

为了配合这个核心决策,我们同步锁定了以下技术选择:

| 类别 | 选择 | 原因(简短) |
|------|------|------------|
| 应用框架 | Next.js 14 | 已有大量 spec 基于此设计,沉没成本 + 生态最强 |
| 部署 | 阿里云 SAE | 国内对标 Vercel 的产品,运维成本最低 |
| 数据库 | 阿里云 RDS PostgreSQL | 比 MySQL 更适合带 JSON 字段的复杂业务 |
| 缓存 | 阿里云 Tair(Redis 兼容) | 标准选择 |
| 对象存储 | 阿里云 OSS | 替代 Supabase Storage |
| 认证 | NextAuth.js v5 | 替代 Supabase Auth,自建更灵活 |
| ORM | Prisma | TypeScript 类型推导最好,AI 代写出错率最低 |
| 邮件 | 阿里云 DirectMail | 替代 Resend(Resend 国内不稳定) |
| 支付 | 微信支付 + 支付宝 | 国内用户付费必备 |
| 错误监控 | Sentry | 行业标准,有国内节点 |
| 产品分析 | 神策数据 | 替代 PostHog(PostHog 国内不稳定) |
| 代码托管 | Gitee 私有仓库(主)+ GitHub 镜像 | 国内访问稳定 + 海外备份 |

---

## 什么情况下会推翻这个决策?

**写下"推翻条件"是 ADR 的重要部分**,它让未来的我们知道什么时候该重新评估。

我们会重新考虑这个决策,如果:

1. **海外用户占比超过 60%**——重心转移时,可能需要把主部署搬回 Vercel
2. **Vercel 在中国推出官方合规服务**——这会改变整个游戏规则
3. **阿里云 SAE 出现重大问题**——需要切换到其他国内云厂商
4. **用户量超过 10 万**——可能需要专门的运维团队,基础设施选择会重新评估
